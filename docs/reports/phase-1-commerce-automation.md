## Verified installed behavior

Evidence is installed Mercur 2.3.3 and Medusa 2.18.0 source, not a financial integration test.

1. **Split payment ownership:** `@mercurjs/core/.medusa/server/src/workflows/cart/workflows/complete-cart-with-split-orders.js` deliberately does not create direct order/payment-collection links. All seller orders reach the single collection through `order.cart.payment_collection`. It also creates the order/cart, seller/order and order-group/order links. Cancellation and capture eligibility must derive the complete group from persisted links rather than accept caller-supplied seller IDs.
2. **Cancellation scope:** Medusa `@medusajs/core-flows/dist/order/workflows/cancel-order.js` traverses only `order.payment_collections`, cancels uncaptured linked payments, refunds captured linked payments and marks those collections canceled. For the native Mercur topology above, the shared cart collection is absent from that relation, so native cancellation can preserve its authorization. Before reuse, validate that no direct collections exist, that the split has no active fulfillments and that it remains eligible under the group lock. Legacy or mixed topologies must fail closed; blindly calling the workflow against an order with a direct shared payment link could cancel/refund the buyer payment.
3. **Partial-capture overcharge hazard:** Medusa payment-module `capturePaymentFromProvider_` passes `payment.data` and capture-ID context to the provider, but does not pass the requested capture amount. The installed Stripe provider's `capturePayment` calls `paymentIntents.capture(id, { idempotencyKey: context?.idempotency_key })` without `amount_to_capture`. Therefore a smaller amount recorded by native `capturePaymentWorkflow` does **not** establish that Stripe captures that smaller amount. Automating the requested split policy with that call unchanged is unsafe.
4. **Partial-capture bookkeeping:** The payment module sets `captured_at` only when the recorded captures reach the original payment amount. Its collection status compares capture totals against the original collection amount. A reduced final capture requires explicit reconciliation of the retained total and completion semantics; leaving an apparently authorized remainder can cause repeat processing.
5. **Webhook repeat risk:** Mercur `workflows/payment/workflows/process-payment.js` handles a successful payment event by calling `capturePaymentWorkflow` again with the webhook amount. The final reduced capture must be safely recognizable when this happens; recording a partial local capture while leaving `captured_at` empty is insufficient protection.
6. **Order accounting:** `capturePaymentWorkflow` creates order transactions only through the direct `order_payment_collection` link. Native Mercur splits have no such link. The split completion workflow allocates pre-existing captures proportionally at checkout, but this does not implement later capture allocation. Automation must record each retained split's precise final total against the actual capture, without assigning money to canceled splits or duplicating order transactions.
7. **Native payouts are caller-guarded:** `workflows/payout/workflows/create-payout.js` reads the order, seller/account and item/shipping commission lines; computes order total minus commission; sends order ID as the idempotency key; and links the result to the seller. It does not establish captured/fulfilled/timing eligibility or inspect the disabled option. `PayoutModuleService.createPayouts` checks native ACTIVE status, calls the provider and then creates the native payout row. Provider success followed by local persistence failure remains a recovery boundary requiring investigation before automatic retry. Provider idempotency must not be treated as a permanent local uniqueness guarantee.
8. **Vendor capture access:** Ownership of any seller split can authorize access to the common buyer payment's native vendor capture route. Root reports an unconditional rejection guard for `POST /vendor/payments/:id/capture`; this worker did not edit that middleware.
9. **Cancellation concurrency:** Native `cancel-order.js` validates active fulfillments and then separately mutates orders, reservations and direct linked payments. It does not serialize other native fulfillment/order-edit/link writers with the evaluator. A scheduler-only lock cannot close that race. Root must establish and verify a common native writer boundary before enabling cancellation.
